# Security review

Date: 2026-10-26. Version reviewed: 0.1.0, before the first release. The repository is public with 3 commits on `main`; the distribution files below were reviewed uncommitted.

## Scope

Everything in the repository except build output (`.build/`, `build/`) and the local Python virtual environment (`.venv/`): the menu bar app (`Sources/BlackSharkBattery`), the `BatteryCore` library and its tests, `build.sh`, `Package.swift`, the Python reference script and `requirements.txt`, and the distribution files: the one-line installer `install.sh`, the Homebrew cask `Casks/blackshark-battery.rb`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `compose.yaml`, `Makefile` and the `.gitignore` change. README, CLAUDE.md, CHANGELOG and LICENSE were checked for personal data.

The repository settings that matter for the release path were read through the GitHub API (read only): private vulnerability reporting, immutable releases, rulesets, branch protection on `main` and the default workflow token permissions.

Out of scope: notarization. The author has no Apple Developer ID, so the app is signed ad hoc and the install routes remove the quarantine flag. That choice is accepted; finding 1 states what it costs.

## Method

1. Read every file in scope line by line, and compared `install.sh`, the cask and both workflows with the reviewed versions in natural-scroll-toggle, which they were ported from.
2. Searched the tracked and the new untracked files (36 in total) for secrets and personal data: home-directory paths, e-mail addresses, `ghp_`, `gho_`, `github_pat`, `xox`, `AKIA`, private key headers, `password`, `secret`, `token`, `serial`, uid 501 and session ids. Searched `Sources` for APIs that ask for permissions, start processes, load code or use the network (`IOHIDRequestAccess`, `URLSession`, sockets, `Process`, `dlopen`, event taps, `IOHIDManagerOpen`).
3. Re-ran the installer building-block tests from the natural-scroll-toggle review on this Mac (macOS 27), with throwaway files in a scratch directory outside the repository, because the results depend on the macOS tools and not on the project: `xattr -dr` on trees with and without the attribute and with symlinks to a file and to a directory outside the tree; `ditto -x -k` on four crafted archives (`../` entries, an absolute path, a symlink followed by an entry written through it, a symlink pointing outside); `shasum -a 256 -c` on ten good and malformed sums files.
4. Fed 15 crafted `SHA256SUMS` files to the installer's own parsing lines (`install.sh:96-114`, copied unchanged into a test script) to see which hashes and asset names it accepts.
5. Checked every byte prefix of `install.sh` (5,253 prefixes of a 5,254-byte file) with `bash -n`, which parses without running anything, and listed the last top-level line of every prefix that parses. The natural-scroll-toggle review executed each prefix against logging stubs; that was not repeated here, because executing fragments of the installer was outside what this review was allowed to do. Parsing is enough to show which top-level commands a cut-off download can reach.
6. Ran `./install.sh --dry-run`, the same through a pipe with `BSB_VERSION` and an `INSTALL_DIR` containing a space, `--help` and an unknown option.
7. Checked the tag regular expression in `release.yml` under `bash` against 17 good and hostile tag names, 10 of them again under `bash`, the shell the runner uses, and confirmed through the GitHub API that the pinned `actions/checkout` commit is the `v4.4.0` and current `v4` tag.
8. Ran `docker compose run --rm lint-shell`, `docker compose run --rm lint-actions` (both exit 0; the image has actionlint 1.7.12 with shellcheck bundled, so `run:` blocks are checked too) and `brew style Casks/blackshark-battery.rb` with Homebrew 7.0.10 from inside the repository (no offenses; with `--cask` it refuses a cask outside a tap). Nothing was installed, tapped, tagged or released, and nothing was sent to the headset.

Severity is rated by what an attacker gains and what they need first. A finding that needs write access to the repository is rated by what it adds on top of that access, which is usually nothing.

Nothing was fixed in this round. The findings with status Open carry a recommendation for the maintainer.

## Where the findings are

Findings 2, 4, 6, 10, 11, 12, 13, 14 and 18 concern the distribution files added after 0.1.0 was committed: `install.sh`, `Casks/blackshark-battery.rb`, `.github/workflows/ci.yml`, `.github/workflows/release.yml` and `compose.yaml`. Findings 3 and 17 are in `build.sh`, and 15 and 16 in the app sources, which were committed first.

## What a compromised app could do

A replaced or backdoored `BlackSharkBattery.app` runs as the logged-in user, outside any sandbox, with quarantine removed. It could read and change whatever that user can reach (home directory files outside the privacy-protected folders, the user's preferences, the network, a login item through `SMAppService`), and it could open the dongle and send it anything, including the EQ, sidetone, idle timer and firmware commands the OpenRazer driver defines, or open any other HID device that has no `RequiresTCCAuthorization` property. It could not become root without the user's password, and it could not read the keyboard, a Logitech receiver, the screen or protected folders without macOS first showing a permission prompt, because the genuine app holds none of those permissions. The genuine app, if an attacker controls only its inputs (the dongle's replies, its own preferences, `argv`), can be made to show a wrong battery level or a "bad reply" state, and nothing more.

## Residual risk

- Notarization: none. Users trust the GitHub account and the release workflow directly, Apple never scans the binary, and a bad release cannot be revoked by Apple. Finding 1.
- `curl | bash` trust: running the installer trusts whatever is on `main` at that moment, fetched over TLS from GitHub. The hash in `SHA256SUMS` protects the transfer, not the source. Anyone who can push to `main` or publish a release (the owner, a stolen token, the release job itself) can ship code that runs with the user's rights. Findings 2 and 12.
- Hardware: the four frames come from Synapse USB captures via OpenRazer PR #2862 and HaloBattery, not from Razer documentation. The review checks that the app sends only those frames, not what the headset firmware does with them.
- Homebrew trust: the cask lives in a personal tap. Users who run `brew trust` on the whole tap also trust any future cask added to this repository.
- Runner images: releases are built on `macos-latest`, whose toolchain changes without notice. A compromised GitHub-hosted image would affect every project that builds there, not only this one.
